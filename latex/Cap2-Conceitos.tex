Para desenvolver um \textit{dongle} seguro, é necessário entender, primeiramente, o contexto no qual este dispositivo atuará, as especificações às quais ele deve sujeitar-se e as possibilidades que fornecerá ao seu usuário.

A coleta dos dados é possibilitada pela existência da rede CAN, uma rede veicular que toma a forma de um barramento de dois fios, pelos quais trafegam as mensagens trocadas entre as ECUs. Ela será devidamente detalhada na \autoref{sec:CAN}; presentemente basta identificar que a rede CAN define somente as camadas física e de dados. Um protocolo de alto nível é necessário para gerenciar a comunicação e padronizar as mensagens.

Neste contexto, o protocolo OBD-II é adotado. Ele especifica, entre outros, a forma da comunicação, que ocorre no modelo requisição-resposta, e o formato das mensagens e dos dados nelas contidos. Também será oportunamente detalhado na \autoref{sec:OBD}. 

Nota-se que um dispositivo que deseje participar de comunicação OBD-II com um automóvel deve conectar-se à rede CAN do carro e saber modular suas mensagens nos dois fios que compõem o barramento, bem como identificar neles a resposta à sua requisição. Este é um processo trabalhoso e convidativo à abstração. Isto levou ao surgimento do ELM327, um \textit{dongle} que se conecta à porta OBD-II e fornece uma interface serial para um cliente, comumente um PC, que pode enviar e receber mensagens ASCII, as quais serão traduzidas para o formato das mensagens OBD-II. 

A implementação do \textit{dongle} proposto tomará, como modelo, o ELM327, contando com uma camada responsável por receber e enviar caracteres, processar comandos de autoconfiguração, e filtrar mensagens. Os pontos relevantes do ELM327 serão detalhados na \autoref{sec:ELM}.

O microcontrolador escolhido para a implementação do \textit{dongle} proposto 
é o ESP32, um sistema em chip (SoC) que integra, entre outros periféricos, 
um controlador CAN e um módulo de comunicação Bluetooth, tornando-o adequado 
para os requisitos do projeto. Para possibilitar a integração do 
\textit{dongle} com um aplicativo móvel, optou-se pela utilização do 
Bluetooth Low Energy. Já para a programação do ESP32, optou-se pela 
utilização do FreeRTOS, um sistema operacional de tempo real que permitirá 
a organização do firmware em tarefas concorrentes, e do PlatformIO, ambiente 
de desenvolvimento que facilita o gerenciamento de dependências e a 
compilação do projeto.

\section{Controller Area Network (CAN)} \label{sec:CAN}


\subsection{Visão geral}
A rede CAN é um sistema de comunicação serial com topologia em barramento, inicialmente especificada pela BOSCH na década de 80. É utilizada em veículos com o intuito de permitir que unidades de controle eletrônico (ECUs, do inglês \textit{Electronic Control Units}) comuniquem-se umas com as outras, sem a necessidade de um computador central \cite{csselectronics_can_intro}.

Foi desenvolvida com um grande foco em confiabilidade, oferecendo vantagens como: resistência a ruídos e a interferências eletromagnéticas; autodiagnósitco; detecção de erros e retransmissão automática; e arbitragem não destrutiva \cite{Bozdal2020CAN}.

Há algumas variantes do CAN, nomeadamente: o CAN clássico e o CAN FD (\textit{Flexible Data-rate}), ambos definidos na ISO 11898-1; o CAN de alta velocidade, definido na ISO 11898-2; e o CAN de baixa velocidade, definido na ISO 11898-3 \cite{boland2021overview}. O presente trabalho restringe-se às variantes adotadas em veículos de passeio para diagnóstico OBD-II: o CAN clássico de alta velocidade, conforme as normas ISO 11898-1 e ISO 11898-2.

\subsection{Funcionamento da comunicação}

Fisicamente, o barramento CAN conta com dois fios, o CAN\_H e o CAN\_L, que compõem um par trançado com sinalização diferencial. Deste modo, o valor lógico em um determinado momento não é ditado pelo valor absoluto da tensão em relação a um terra, mas sim pela diferença na tensão entre o CAN\_H e o CAN\_L \cite{Bozdal2020CAN}.  

A comunicação é orientada a mensagens, que tomam forma de quadros no barramento. Neste contexto, a ISO 11898-1 define a camada de dados (\textit{Data Link Layer}), que especifica: os tipos de quadros (de dados, de erro, remotos e de \textit{overload}); os métodos de detecção e tratamento de erros; e técnicas de arbitragem para evitar colisões \cite{csselectronics_can_intro}.

Um quadro de dados possui os campos listados abaixo e explicitados na imagem \autoref{fig:sinalizacao-diferencial}) \cite{Bozdal2020CAN}.


\begin{figure}[H]
    \centering
    \includegraphics[width=0.7\textwidth]{assets/cap2-conceitos/quadro-dados.png}
    \caption{Campos de um quadro de dados CAN.}
    \label{fig:sinalizacao-diferencial}
    \fonte{Adaptado de \cite{csselectronics_can_intro}}
\end{figure}


\begin{itemize}
    \item \textbf{SOF} (\textit{Start Of Frame}): sinaliza o início da transmissão;
    \item \textbf{ID} (\textit{Identifier}): define a prioridade do quadro (valores menores representam prioridade maior) e o tipo de mensagem. Possui 11 bits no formato padrão (CAN 2.0A) ou 29 bits no formato extendido (CAN 2.0B);
    \item \textbf{RTR} (\textit{Remote Transmission Request}): distingue um quadro de dados de um quadro de transmissão remota;
    \item \textbf{Control}: possui o bit de identificador de extensão (IDE, do inglês \textit{Identifier Extension}), que é '0' se ID é de 11 bits. Também possui o código de tamanho de dados (DLC, do inglês \textit{Data Length Code}), que possui 4 bits e especifica a quantidade de bytes de dados sendo transmitidos (de 0 a 8); 
    \item \textbf{Data}: contém os bytes de dados;
    \item \textbf{CRC} (\textit{Cyclic Redundancy Check}): utilizado para verificar a integridade dos dados;
    \item \textbf{ACK}: indica se o nó reconheceu e recebeu os dados corretamente;
    \item \textbf{EOF}: indica o fim do quadro.
\end{itemize}


Uma ECU conectada ao barramento consiste em 3 elementos principais: um microcontrolador; um controlador CAN; e um transceptor CAN. O microcontrolador interpreta mensagens CAN recebidas e decide quais transmitir, baseado em sua programação. O controlador CAN remove complexidade do microcontrolador ao dedicar-se à garantia de que a comunicação seja aderente ao protocolo, e suas responsabilidades incluem, mas não se limitam, a: codificação e decodificação de quadros; cálculo do CRC; confirmação (ACK); detecção de erros; e arbitragem. Por sua vez, o transceptor CAN conecta-se ao barramento CAN, e é responsável por receber os dados do controlador e convertê-los aos sinais diferenciais do barramento, e vice-versa. \cite{csselectronics_can_intro}

\begin{figure}[H]
    \centering
    \includegraphics[width=0.7\textwidth]{assets/cap2-conceitos/diagrama-barramento-can.png}
    \caption{Diagrama de um barramento CAN com ECUs}
    \label{fig:barramento-can}
    \fonte{Adaptado de \cite{Bozdal2020CAN}}
\end{figure}

Com isto, são conhecidos os mecanismos que permitem a uma ECU colocar um quadro no barramento, e receber os que nele são transmitidos. Nota-se, entretanto, que o CAN especiffica \textit{como} um quadro trafega, mas o significado dos bytes do campo DATA, os IDs utilizados, e as regras da troca de mensagens precisam ser especificadas por um protocolo de camada superior \cite{csselectronics_can_intro}. No contexto do diagnóstico veicular, este papel é desempenhado pelo OBD-II, cuja apresentação encontra-se na próxima seção.

\section{Protocolo OBD-II} \label{sec:OBD}

\subsection{Visão geral}
O OBD-II é um protocolo padronizado de autodiagnóstico para veículos, que permite a extração de códigos de diagnóstico de problemas (DTCs, do inglês \textit{Diagnostic Trouble Codes}) e a leitura de dados em tempo real através do conector OBD-II \cite{csselectronics_obd2_intro}. Tornou-se obrigatório no Brasil para todos os veículos leves fabricados a partir de 2010 \cite{conama354_2004}.

Ele que especifica o diagnóstico veicular em diferentes camadas. O conector físico é o definido pela SAE J1962 (ISO 15031-3). Quanto à comunicação, o OBD-II admite diferentes protocolos de camada inferior, dentre os quais o CAN, conforme a ISO 15765-4, que fixa a taxa de transmissão em 250 ou 500~kbit/s, o tamanho do identificador em 11 ou 29 bits e os identificadores CAN utilizados nas requisições e respostas. A troca de mensagens segue o modelo requisição-resposta, com formato definido tanto para mensagens que cabem em um único quadro quanto para aquelas que exigem vários, por meio do protocolo de transporte ISO-TP (ISO 15765-2). Por fim, a SAE J1979 (ISO 15031-5) define os serviços e os identificadores de parâmetros (PIDs, do inglês \textit{Parameter IDs}) padronizados, entre outros aspectos \cite{csselectronics_obd2_intro}.

\subsection{Conector SAE J1962}
O conector físico utilizado é especificado no padrão SAE J1962 / ISO 15031-3, e possui dois tipos: o tipo A, utilizado em veículos leves, e o tipo B, comumente utilizado em veículos pesados. O presente trabalho considerará somente o conector do tipo A para veículos leves. Ele possui em 16 pinos, entre eles: CAN\_H; CAN\_L; terra; e +12V (conectado à bateria).

\subsection{Mensagens OBD-II}

O OBD-II define um modelo requisição-resposta. Um equipamento de diagnóstico, chamado cliente (no nosso caso, o \textit{dongle}), coloca no barramento uma requisição, e as ECUs que dispõem das informações solicitadas respondem \cite{csselectronics_obd2_intro}. Tanto as requisições e as respostas trafegam como quadros de dados CAN (\autoref{sec:CAN}); o que o OBD-II define é o conteúdo dos campos ID e data desses quadros.

\subsubsection{Campo de dados e tipos de mensagens}

Conforme a ISO 15765-4, os quadros CAN de diagnóstico devem utilizar um campo de dados de 8 bytes. Estes 8 bytes contém informações de controle do transporte e os dados da mensagem de diagnóstico.

O protocolo ISO-TP, definido pela ISO 15765-2, permite transmitir mensagens que não cabem em um único quadro CAN. Para isso, define quatro tipos de quadro, identificados pelos quatro bits mais significativos do primeiro byte do campo de dados: \textit{Single Frame} (0), \textit{First Frame} (1), \textit{Consecutive Frame} (2) e \textit{Flow Control Frame} (3). O significado dos demais bits desse primeiro byte depende do tipo de quadro.

\subsubsection{Estrutura das Respostas OBD-II} \label{subsub:isotp}

Uma ECU, ao identificar uma requisição OBD-II que pode responder, gera uma resposta. Se ela couber em um único quadro, a resposta será contida em um quadro do tipo \textit{Single Frame}. Nesse caso, o ID CAN será como descrito na \autoref{subsub:can-id}. 

Tomando o exemplo da requisição na Figura~\ref{fig:exemplo-obd2-req}, será apresentada uma possível resposta, que ilustrará o funcionamento padrão para respostas \textit{Single Frame}, na Figura~\ref{fig:exemplo-obd2-resp}.

No caso de um ID CAN de tamanho de 11 bits, nas respostas, o ID CAN é o ID da requisição da ECU somado a 8. A ECU do motor, por exemplo, recebe requisições endereçadas em \texttt{0x7E0} e responde em \texttt{0x7E8}, e as demais respondem até \texttt{0x7EF}.

Além disso, o \textit{Service} das respostas é 0x40 + o valor do \textit{Service} das requisições. 

Os bytes de dados das respostas, a partir do quarto byte do campo DATA, são nomeados A, B, C, e D. Cada PID terá sua regra de interpretação desses bytes. O PID 0D, por exemplo, representa a velocidade em km/h, e utiliza apenas o \textit{byte} A, sendo a velocidade dada diretamente por

\begin{equation}
v = A \text{ km/h}.
\end{equation}


Com essas informações, é possível ter o seguinte entendimento da resposta na Figura~\ref{fig:exemplo-obd2-resp}:


\begin{figure}[H]
    \centering
    \includegraphics[width=0.7\textwidth]{assets/cap2-conceitos/example-obd2-resp.png}
    \caption{Exemplo de Resposta OBD-II}
    \fonte{Adaptado de CSS Electronics}
    \label{fig:exemplo-obd2-resp}

\begin{itemize}
    \item \textbf{Code}: 0, especificando \textit{Single Frame};
    \item \textbf{Size}: 3, abrangendo o \textit{Service}, o \textit{PID}, e o byte A, utilizado na interpretação da resposta;
    \item \textbf{Service}: 0x41, indicando que é uma resposta a uma requisição ao \textit{Service} 0x01;
    \item \textbf{PID}: 0x0D, repetindo o \textit{PID} solicitado na requisição;
    \item \textbf{A}: 0x3C, que equivale a 60 em decimal; logo, a velocidade do veículo é de 60 km/h;
    \item \textbf{B, C, D e \textit{byte} não utilizado}: \textit{padding}, sem
significado e ignorados na interpretação.
\end{itemize}

Mas também pode ocorrer de uma resposta não caber em um único quadro, já que o campo de dados do CAN clássico possui, no máximo, 8 bytes. Isto acontece, por exemplo, quando o cliente solicita DTCs. Neste caso, o ISO-TP (ISO 15765-2) define o procedimento ilustrado no diagrama de sequência Figura ~\autoref{fig:isotp-seq}, e explicado de maneira simplificada a seguir.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.8\textwidth]{assets/cap2-conceitos/isotp-single-ecu.png}
    \caption{Troca de quadros ISO-TP com uma ECU}
    \fonte{Elaborado pelo autor}
    \label{fig:isotp-seq}
\end{figure}


A primeira resposta será um \textit{First Frame}, de código 1, que conterá um campo com o tamanho total da mensagem, em \textit{bytes}, e os seis primeiros \textit{bytes} de dados, de acordo com a Figura~\ref{fig:iso-tp-msg-kinds}. O cliente, por sua vez, ao identificar que recebeu um \textit{First Frame}, deve enviar um \textit{Flow Control}, de código 3, ao ID de requisição da ECU (por exemplo, \texttt{0x7E0} para a ECU que respondeu em \texttt {0x7E8}). Esse quadro autoriza a ECU a continuar a transmissão e define seus parâmetros: o \textit{Block Size}, que é a quantidade de \textit{Consecutive Frames} que a ECU pode enviar antes de aguardar novo \textit{Flow Control} (0 indica que pode enviar todos), e o \textit{STmin}, que é o tempo mínimo entre dois \textit{Consecutive Frames}. Em seguida, a ECU enviará \textit{Consecutive Frames}, de código 2, que possuem um campo de índice de sequência (de 4 bits, iniciando em 1 e voltando a 0 após F) e até sete \textit{bytes} de dados cada. O cliente concatena os dados recebidos até atingir o tamanho total informado no \textit{First Frame}.

Se mais de uma ECU responder, o cliente receberá mais de um \textit{First Frame}, e deve enviar um \textit{Flow Control} para cada um deles. Também deve armazenar o ID de cada \textit{First Frame}, para reconstruir a mensagem de cada ECU a partir dos seus \textit{Consecutive Frames}, que podem chegar intercalados. Este caso é ilustrado no diagrama de sequência da \autoref{fig:isotp-seq-multi}.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.8\textwidth]{assets/cap2-conceitos/isotp-multi-ecu.png}
    \caption{Troca de quadros ISO-TP com múltiplas ECUs}
    \fonte{Elaborado pelo autor}
    \label{fig:isotp-seq-multi}
\end{figure}

Um algoritmo em pseudocódigo para lidar com múltiplas respostas ISO-TP é dado
a seguir:

\begin{verbatim}
mensagens = {}

para cada quadro recebido:
    se quadro e Single Frame:
        entrega(quadro.dados)

    senao se quadro e First Frame:
        mensagens[quadro.id] = {
            tamanho: quadro.tamanho,
            dados:   quadro.dados,
            proximo: 1
        }
        envia Flow Control para (quadro.id - 8)

    senao se quadro e Consecutive Frame e quadro.id em mensagens:
        m = mensagens[quadro.id]
        se quadro.indice != m.proximo:
            descarta mensagens[quadro.id]      # quadro perdido
        senao:
            m.dados += quadro.dados
            m.proximo = (m.proximo + 1) mod 16
            se tamanho(m.dados) >= m.tamanho:
                entrega(m.dados[0 : m.tamanho])  # remove padding
                remove mensagens[quadro.id]
\end{verbatim}
